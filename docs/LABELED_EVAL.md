# 带标注流量评测（CTU-13）

> 数据：CTU-13（CC-BY，Garcia et al. 2014），`scripts/fetch_ctu13.py` 下载。
> 样本：场景 1 · `botnet-capture-20110810-neris.pcap` · 分析 323154 个包。

## 为什么要换数据集

`benchmark_real.py` 那 30 份精选 pcap 里几乎没有正常背景流量——它能回答「能不能检出」，回答不了「会不会误报」。CTU-13 是同一条链路上「僵尸网络 + 正常 + 背景」混采一小时，逐流带标注，才能算误报率。

## 结果（流级）

| 指标 | 值 |
|---|---:|
| 流总数 | 46712（恶意 40959 / 正常 5753）|
| 召回率 recall | **0.680** |
| 误报率 FPR | **0.0068** |
| 精确率 precision | 0.999 |
| 混淆矩阵 | TP 27843 / FN 13116 / FP 39 / TN 5714 |

## 跨场景对比

| 场景 | 感染家族 | 裁剪后流数 | recall | FPR | precision |
|---|---|---:|---:|---:|---:|
| 1 | Neris（IRC + DGA + 垃圾邮件）| 46,712 | **0.680** | 0.0068 | 0.999 |
| 8 | Murlo（Qvod 播放器）| 268,428 | 0.234 | 0.0003 | 0.946 |
| 3 | Rbot | 72,115 | **0.000** | 0.0054 | 0.000 |
| 12 | Sogou | 6,449 | 0.005 | 0.0000 | 1.000 |

结论很直接：**检测器只对「有量级特征」的僵尸网络有效**（Neris 的 DNS/SMTP 洪泛），对 Rbot 这种低频 IRC 心跳几乎零召回。这不是调参问题——Rbot 场景里感染主机的恶意流集中在 1027/53/80，量很小，既没有 DNS 洪泛也没有扫描扇出，当前没有任何规则描述「低频 IRC C2」。要提升得补 `irc_c2` 这类「少量但周期性」的检测，而不是继续调阈值。

## 为什么召回不是 100%

这份样本里 76% 的恶意流是**感染主机的 DNS 请求**（2.1 万条）、15% 是 SMTP 投递尝试。如果只靠原来那套「端口扫描 / 爆破 / 心跳 / 隧道」检测器，召回只有 2.9%：单看每一条 DNS 查询都是合法的，异常在**量级**上。

所以补了两个行为检测器（都是通用规则，不是给这个样本写死的）：

- `dns_volume`：单主机 DNS 查询量超过阈值（默认 5000 次）→ 覆盖 DGA / 隧道 / 邮件投递前置；
- `smtp_fanout`：单主机向 50+ 个不同目标发 SMTP → 垃圾邮件僵尸。

两个检测器命中时会在 `metrics.scope` 里给出**精确五元组**，评测按五元组匹配，不做模糊的端点覆盖（试过端点口径：正常 DNS 流会和告警共享 `:53`，误报率虚高到 95%，已废弃）。

还有一点：Suricata 对这份 2011 年的 IRC 僵尸网络样本**零告警**——ET Open 里没有 Neris 的规则。这正是「签名靠规则覆盖、行为靠统计规律」的分工，也解释了为什么精选样本能到 100%：那 30 份里大量样本是有公开规则的常见家族。

## 口径与局限

- **流级匹配**：告警五元组与 binetflow 记录（任一方向）相同即算命中；binetflow 里同一五元组会出现多条记录（尤其 DNS 复用源端口），所以**召回偏乐观**，别把它当成包级召回；
- 我们的检测器是「按 pcap 聚合」的（如端口扫描、心跳），天然比逐流分类器粗，这个口径对它是相对公平的；
- CTU-13 是 2011 年的 IRC 僵尸网络，不是加密 C2；结论不能外推到现代对抗流量。
