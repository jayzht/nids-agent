# 带标注流量评测（CTU-13）

> 数据：CTU-13（CC-BY，Garcia et al. 2014），`scripts/fetch_ctu13.py` 下载。
> 样本：场景 1 · `botnet-capture-20110810-neris.pcap` · 分析 323154 个包。

## 为什么要换数据集

`benchmark_real.py` 那 30 份精选 pcap 里几乎没有正常背景流量——它能回答「能不能检出」，回答不了「会不会误报」。CTU-13 是同一条链路上「僵尸网络 + 正常 + 背景」混采一小时，逐流带标注，才能算误报率。

## 结果（流级）

| 指标 | 值 |

| 8 | Murlo（Qvod 播放器）| 268,428 | **0.947** | 0.0014 | 0.941 |

场景 12 几乎无召回，是**数据问题**而非检测问题：它的 pcap 只覆盖 2 分钟（08:41–08:43），而 binetflow 覆盖 10:32–11:31，两者不是同一时间窗，能对上的流只有 6 千条、且几乎没有恶意流落在里面。

### 数据量一大，光有「证据」不够：覆盖规则

IoT-23 的 Hide-and-Seek 场景有 **53 万条恶意流**，全部是感染主机对23/2323/8080/9527 端口的扇出。第一版 recall 只有 **0.016**——两个原因：

1. `horizontal_scan` 只看「发了 SYN 但没有数据」的连接，而这类爆破/蠕虫连接**握手会完成**，整批被排除；`repeated_attempts` 又要求同一目标 >= 20 次，而扇出场景每个目标只试一两次。→ 补了 `fanout_attempts`（短连接按「源 + 目的端口」聚合，覆盖 >= 50 个不同目标即告警）。
2. 告警只带精确五元组的话，53 万条流根本装不下（`scope` 上限 5 万）。所以给检测器加了 **`scope_rules`**：一条 `{"src": "192.168.100.103", "dport": 23}` 就精确表达了「这台主机扫了这批主机的 23 端口」，评测器按规则匹配——**从 O(流数) 的内存换成 O(规则数)**。

改完：IoT-23 recall 0.016 → **1.000**（FPR 0.0002），CTU-13 三个场景也顺带从 0.90/0.98/0.95 提到 **0.99/1.00/0.95**。

### 从 0.000 到 0.983：两个改动

Rbot 场景一开始 recall 是 **0.000**，但检测器其实报了 `horizontal_scan`（.165 横向扫了 2.8 万台主机的 22 端口）。问题不在检测，在**证据粒度**：

1. **告警只带 12 个证据帧**，标注是按流匹配的，于是 2.7 万条恶意流只匹配上 10 来条。改成让 `port_scan / horizontal_scan / repeated_attempts / beacon / irc_c2`都在 `metrics.scope` 里给出**精确五元组集合**后，召回直接到 0.98。
2. **补 `irc_c2` 检测器**：Rbot 的 C2 只有 63 条流、端口 6667，既不是扫描（单端口单目标）也不是 beacon（间隔方差大），之前的规则一条都不响。新规则用「端点落在 IRC 端口 + 同一被控端累计 ≥3 条会话」判定，并合并「两侧各报一次」和「多客户端连同一服务器」的重复告警。

### 误报率为什么从 0.7% 涨到 3~6%

不是检测变差了，而是**口径变了**：scope 让告警覆盖它真正描述的所有流之后，被计入「误报」的流里包含大量其实也是恶意的流量——CTU-13 只给**已知感染主机**相关的流打 botnet 标签，外部主机打进这台主机的扫描/爆破尝试仍标成 `Background`。所以这里的 FPR 是**标签口径下的上界**，不是真实误报率。

## 为什么召回不是 100%

场景 1 里 76% 的恶意流是**感染主机的 DNS 请求**（2.1 万条）、15% 是 SMTP 投递尝试。如果只靠原来那套「端口扫描 / 爆破 / 心跳 / 隧道」检测器，召回只有 2.9%：单看每一条 DNS 查询都是合法的，异常在**量级**上。

所以补了两个行为检测器（都是通用规则，不是给这个样本写死的）：

- `dns_volume`：单主机 DNS 查询量超过阈值（默认 5000 次）→ 覆盖 DGA / 隧道 / 邮件投递前置；
- `smtp_fanout`：单主机向 50+ 个不同目标发 SMTP → 垃圾邮件僵尸。

两个检测器命中时会在 `metrics.scope` 里给出**精确五元组**，评测按五元组匹配，不做模糊的端点覆盖（试过端点口径：正常 DNS 流会和告警共享 `:53`，误报率虚高到 95%，已废弃）。

还有一点：Suricata 对这份 2011 年的 IRC 僵尸网络样本**零告警**——ET Open 里没有 Neris 的规则。这正是「签名靠规则覆盖、行为靠统计规律」的分工，也解释了为什么精选样本能到 100%：那 30 份里大量样本是有公开规则的常见家族。

## 口径与局限

- **流级匹配**：告警五元组与 binetflow 记录（任一方向）相同即算命中；binetflow 里同一五元组会出现多条记录（尤其 DNS 复用源端口），所以**召回偏乐观**，别把它当成包级召回；
- 我们的检测器是「按 pcap 聚合」的（如端口扫描、心跳），天然比逐流分类器粗，这个口径对它是相对公平的；
- CTU-13 是 2011 年的 IRC 僵尸网络，不是加密 C2；结论不能外推到现代对抗流量。
